# Zed Browser Agent Context Bridge

## Problem

The embedded browser exists inside Zed, but the agent chat does not yet treat it
as a first-class context source. When a user types `@browser`, the current agent
stack can drift toward the external Codex Desktop Browser plugin instead of the
active Zed `BrowserView`. That makes the model say things like "iab is not
available" even though the user is looking at a Zed browser tab.

The browser cursor work gives Zed a local preview-and-click path. The missing
layer is a Zed-native bridge between the agent composer and the active embedded
browser tab.

## Goal

Make `@browser` in Zed mean the active embedded browser tab.

The agent should be able to:

- see the current embedded browser page URL and title;
- see the current design-mode selected element, when present;
- see the current agent cursor preview, when present;
- ask Zed to resolve a described element in the active browser tab;
- preview the target before clicking;
- click the previewed target through native WebView2 input.

## Non-Goals

- Do not call the Codex Desktop Browser plugin for Zed browser state.
- Do not use Chrome extension tabs as a fallback for embedded browser context.
- Do not add a detached browser window.
- Do not replace the WebView2 composition browser.

## User Experience

### Mention

Typing `@browser` in the agent composer should insert a compact chip labelled
`Browser`.

The expanded context sent to the model should be concise:

```text
Zed embedded browser:
- URL: http://localhost:3004/owned
- Title: Owned Books
- Selected element: button "Remove"
- Selector: button[data-testid="remove-book"]
- Bounds: x=1204, y=428, width=36, height=32
```

If there is no active browser tab:

```text
No active Zed browser tab is open. Open one with browser::NewTab.
```

### Commands

The agent should prefer Zed-native browser commands:

```text
browser.current_page()
browser.find_element({ text: "Sign in" })
browser.find_element({ selector: "button[type=submit]" })
browser.preview_click(target)
browser.click_previewed()
browser.clear_cursor()
```

V1 can implement these as Zed actions routed to the active `BrowserView`.
Later ACP/tool integration can expose them as formal agent tools.

### Natural Language

When the user says:

```text
open localhost:3004 and click Sign in in @browser
```

the agent should:

1. target the active Zed browser tab, or open one if none exists;
2. navigate it to `http://localhost:3004`;
3. resolve the visible `Sign in` element;
4. show the cursor preview;
5. ask for confirmation unless the user explicitly requested immediate click;
6. click through native WebView2 input.

## Data Contract

Add a lightweight browser context snapshot:

```rust
pub struct BrowserAgentContext {
    pub url: String,
    pub title: Option<String>,
    pub selected_element: Option<BrowserResolvedElement>,
    pub previewed_target: Option<BrowserResolvedElement>,
}
```

The snapshot should be generated by `BrowserView`, because it owns the live
browser state. Agent UI should consume this through actions or a small registry,
not by depending on WebView2 internals.

## Required Implementation Stages

1. Add a Zed-native browser mention URI, for example
   `zed:///agent/browser/current`.
2. Teach the agent mention parser and chip renderer to display that URI as
   `Browser`.
3. Add a completion entry so `@browser` appears in the agent composer.
4. Add a browser context request path from agent UI to the active `BrowserView`.
5. Serialize a concise `BrowserAgentContext` into the user message context.
6. Route browser resolve/click actions to the active `BrowserView`.
7. Report a clear error when no active browser tab exists.

## Acceptance Criteria

- `@browser` appears in Zed's agent composer completion list.
- Inserting `@browser` creates a `Browser` chip, not a wall of text.
- Sending a prompt with `@browser` gives the model the active embedded browser
  URL and selected/previewed element context.
- The model does not invoke or mention the Codex Desktop Browser plugin for Zed
  embedded browser tasks.
- Browser resolve and click commands target the active Zed `BrowserView`.
- If no browser tab is active, the user sees a clear Zed-native error.
- Existing file, symbol, diagnostics, thread, skill, and selection mentions
  continue to work.
